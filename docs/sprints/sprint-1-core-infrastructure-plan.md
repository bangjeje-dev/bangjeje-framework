# Bangjeje Framework

## Sprint 1 — Core Infrastructure

### 1. Sprint Objective

Establish the core runtime, global configuration, and Vue 3 plugin infrastructure for the Bangjeje Framework within the `@bangjeje/core` package. This creates the required foundation for future UI and theming packages without introducing any actual components or design tokens at this stage.

### 2. Current Repository Context

The repository is a monorepo currently containing multiple packages (`core`, `ui`, `theme`, `tokens`, etc.) and applications (`playground`, `docs`, `showcase`). Sprint 0 has already laid down the initial workspace configuration and scaffolding. The current `@bangjeje/core` package is essentially empty, lacking build tooling, plugin definitions, and configuration providers.

### 3. @bangjeje/core Architecture

The `@bangjeje/core` package acts strictly as the orchestrator and dependency injection layer for the framework. It will export the main Vue plugin (`BangjejeUI`), global configuration interfaces, and composables for config consumption. It is decoupled from any specific UI implementation.

### 4. Vue Plugin Architecture

We will utilize the Vue 3 `Plugin` interface (`install` method). The `BangjejeUI` plugin will accept a user-defined configuration object, merge it with framework defaults, and `provide` the resolved configuration to the entire Vue application instance.

### 5. Global Configuration Architecture

A type-safe `BangjejeConfig` interface will be defined to represent all global framework settings. A `mergeConfig` utility will combine user-provided `BangjejePluginOptions` with the built-in `defaultConfig`.

- `mergeConfig()` will use intentionally simple **shallow merging** for Sprint 1. We will not introduce a generic deep-merge utility.
- The resolved `BangjejeConfig` provided to the application will be treated as **immutable/read-only** for consumers.

### 6. Provider / Injection Architecture

We will use Vue's dependency injection (`provide` / `inject`). A strictly typed `InjectionKey<BangjejeConfig>` will be created. A composable, `useBangjejeConfig()`, will safely wrap the `inject` call, enforcing type safety.

- **Error Handling:** `useBangjejeConfig()` must throw a clear, actionable runtime error when used without the `BangjejeUI` plugin being installed.

### 7. TypeScript Type Architecture

Strict TypeScript typing is mandatory. All public interfaces, plugin options, and injection keys will be consolidated in a `types/` directory. No `any` types will be permitted. Types will be explicitly exported to consumers.

### 8. Public API and Export Strategy

Internal file structures will be hidden from consumers. The `package.json` will utilize the `"exports"` field to route all imports directly to the generated build files. The `exports` field will exactly match the files actually generated by the build (`dist/index.cjs`, `dist/index.mjs`, and `dist/index.d.ts`). Consumers will import exclusively from the package root:
`import { BangjejeUI, useBangjejeConfig } from '@bangjeje/core'`

### 9. Build Strategy

The package needs to compile from TypeScript into CommonJS and ES Modules, while also generating `.d.ts` declaration files. The `"build"` script in `packages/core/package.json` will be integrated into the root TurboRepo `build` pipeline, ensuring `@bangjeje/core` builds cleanly before apps consume it.

### 10. tsup vs tsc Evaluation

- **`tsc` (TypeScript Compiler):** While native and already present, pure `tsc` requires complex setups (multiple `tsconfig` files or scripts) to output both ESM and CommonJS formats simultaneously, which is a requirement for our library build.
- **`tsup`:** A zero-config bundler powered by `esbuild`.
- **Decision:** The plan proposes introducing `tsup` as a `devDependency` inside `@bangjeje/core`. The decision is based on our explicit requirement for a simple library build producing ESM, CJS, and TypeScript declarations without overcomplicating our `package.json`.

**Explicit `tsup` configuration:**

- **Entry:** `src/index.ts`
- **Output Directory:** `dist/`
- **ESM Output:** Enabled (generates `.mjs`)
- **CJS Output:** Enabled (generates `.cjs` or `.js`)
- **Declaration Generation:** Enabled (generates `.d.ts`)
- **Sourcemaps:** Enabled
- **External Dependencies:** Vue must remain external and must not be bundled into `@bangjeje/core`.

### 11. Dependency Boundaries

- Must declare `vue` as a `peerDependency`. The peer dependency range will align exactly with the Vue version already used by the workspace (`^3.5.40`).
- **Strictly independent from:** `@bangjeje/ui`, `@bangjeje/theme`, and `@bangjeje/tokens`.
- No UI libraries or CSS frameworks will be introduced here.

### 12. File Structure

The implementation will introduce the following structure:

```text
packages/core/
├── package.json
├── tsup.config.ts (or inline package.json script)
├── tsconfig.json
├── src/
│   ├── config/
│   │   ├── types.ts
│   │   └── defaults.ts
│   ├── plugin/
│   │   └── index.ts
│   ├── providers/
│   │   └── config-provider.ts
│   ├── types/
│   │   └── index.ts
│   └── index.ts
└── tests/
    └── core.spec.ts (Vitest automated tests)
```

### 13. Verification Strategy

1. **Automated Tests:** Add Vitest to the workspace (or `@bangjeje/core` specifically) to test the Core infrastructure. We will test at minimum:
   - plugin installation
   - configuration resolution
   - configuration injection
   - missing-provider behavior (throws actionable error)
   - public exports
2. **Build Verification:** Run `pnpm --filter @bangjeje/core build` to verify `tsup` generates `dist/` containing ESM, CJS, and declaration files matching `exports`.
3. **Workspace Verification:** Verify clean root workspace builds: `pnpm build`, `pnpm lint`, `pnpm format`.

### 14. Acceptance Criteria

- `docs/sprints/sprint-1-core-infrastructure-plan.md` is approved.
- `BangjejeUI` plugin orchestrates the `BangjejeConfig`.
- `useBangjejeConfig()` provides type-safe configuration injection and throws an error if uninstalled.
- Internal files are not exposed to consumers.
- Build outputs ESM and CJS formats cleanly using explicit `tsup` configuration.
- Vue is externalized properly and peer-dependant on `^3.5.40`.
- Vitest automated tests cover core functionality.
- Workspaces commands pass cleanly.

### 15. Out of Scope

- Expanding the scope beyond Sprint 1.
- Creating or porting UI components (Button, Input, Layouts).
- Implementing the CSS architecture, Tailwind, or Theme configurations.
- Creating the actual design tokens.

### 16. Risks and Trade-offs

- **Trade-off:** Using shallow merge for config avoids the complexity of deep-merge logic, but requires nested configuration objects to be overridden entirely by the consumer. For Sprint 1, this is an intentional simplicity trade-off.
- **Risk:** Circular dependencies if other packages import from `@bangjeje/core` while `@bangjeje/core` tries to import their types.
  - **Trade-off:** Enforced by keeping `@bangjeje/core` strictly foundational. Other packages must depend on `core`, never the reverse.
