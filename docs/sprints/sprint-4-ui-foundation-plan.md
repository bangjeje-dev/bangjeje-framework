# Sprint 4: UI Foundation Architecture Plan

## Sprint Objective

Establish the foundational architecture for the `@bangjeje/ui` component library. This sprint focuses exclusively on defining the structural, stylistic, and accessibility patterns for all future components, while delivering a minimal set of foundational components (`Button`, `Input`) to prove the architecture.

## Current Repository Context

- **`@bangjeje/core`**: Provides the plugin initialization, Dependency Injection (DI) context, and base configuration.
- **`@bangjeje/tokens`**: Houses static primitive scales and semantic schema interfaces without framework dependencies.
- **`@bangjeje/theme`**: Consumes tokens, owns the dynamic theme state, and automatically serializes the active theme into flattened CSS Custom Properties (e.g., `--bjj-colors-primary`) injected into `document.documentElement`.
- **`@bangjeje/ui`**: Currently an empty shell with a basic `package.json`.

## `@bangjeje/ui` Responsibility

`@bangjeje/ui` is the presentation layer. Its strict responsibilities are:

1. Provide highly accessible, semantic Vue 3 components.
2. Consume the token/theme layer via CSS Custom Properties.
3. Expose composable utilities for UI state (e.g., component size, variant resolution).
   It is **not** responsible for business logic, global state, or defining the token schema.

## Dependency Direction

The dependency flow remains strictly unidirectional to prevent circular dependencies:
`@bangjeje/tokens` ← `@bangjeje/theme` ← `@bangjeje/ui`
_(If `@bangjeje/ui` needs configuration injection, it may also depend on `@bangjeje/core`, but it should never be imported by `core` or `theme`)._

## Component Architecture

Components will be authored as Vue 3 Single File Components (SFCs) using `<script setup lang="ts">`.

- **Dumb Components**: Components should be strictly presentational ("dumb"), receiving data via props and emitting events.
- **Slot-First**: Utilize slots for flexible content projection (e.g., prefix/suffix icons in buttons and inputs).

## Component API / Props / Emits Strategy

- **Strict Typing**: All props and emits will be strictly typed using TypeScript interfaces.
- **Naming Conventions**:
  - Standardized HTML attributes pass through natively via `v-bind="$attrs"` (components will use `defineOptions({ inheritAttrs: false })` where a wrapping `div` is necessary).
  - Event names will be consistent (`update:modelValue`, `click`, `focus`, `blur`).

## Variant and State Architecture

To avoid prop bloat, visual states will be managed via dedicated props that map to specific CSS classes.

- **Variants**: `solid` (default), `outline`, `ghost`, `link`.
- **Sizes**: `sm`, `md` (default), `lg`.
- **States**: `disabled`, `loading`, `error`.
  These props will dynamically assemble a predictable class list (e.g., `bjj-btn bjj-btn--solid bjj-btn--md bjj-btn--loading`).

## Token Consumption Strategy

Components must **never** hardcode visual values (e.g., `color: #ff0000` or `padding: 16px`).
Instead, components will strictly consume the CSS Custom Properties generated by `@bangjeje/theme`.

### Exact CSS Variable Naming Contract

The `@bangjeje/theme` token flattener translates camelCase schema keys into kebab-case CSS variables, prefixed with `--bjj-`. UI components MUST strictly adhere to this exact generated convention (pluralization and casing):

- **Colors**: `var(--bjj-colors-[key])` _(e.g., `--bjj-colors-primary`)_
- **Typography**:
  - `var(--bjj-typography-font-family-[key])`
  - `var(--bjj-typography-font-size-[key])`
  - `var(--bjj-typography-font-weight-[key])`
  - `var(--bjj-typography-line-height-[key])`
  - `var(--bjj-typography-letter-spacing-[key])`
- **Spacing**: `var(--bjj-spacing-[key])` _(e.g., `--bjj-spacing-2`)_
- **Radius**: `var(--bjj-radius-[key])` _(e.g., `--bjj-radius-md`)_
- **Shadows**: `var(--bjj-shadows-[key])` _(e.g., `--bjj-shadows-sm`)_
- **Breakpoints**: `var(--bjj-breakpoints-[key])` _(e.g., `--bjj-breakpoints-md`)_
- **Z-Index**: `var(--bjj-z-index-[key])` _(e.g., `--bjj-z-index-dropdown`)_

**Example Component Consumption:**

```css
.bjj-btn {
  background-color: var(--bjj-colors-primary);
  border-radius: var(--bjj-radius-md);
  padding: var(--bjj-spacing-2) var(--bjj-spacing-4);
  font-family: var(--bjj-typography-font-family-base);
}
```

## Theme Integration

Components are entirely decoupled from the _logic_ of the theme engine. They do not import `useTheme` or check if the theme is "light" or "dark". They rely entirely on the fact that `@bangjeje/theme` ensures the correct `--bjj-*` variables are available in the DOM.

## Accessibility Strategy (WAI-ARIA)

Accessibility is a first-class citizen:

- **Semantic HTML**: Use `<button>` for buttons, `<input>` for inputs.
- **ARIA attributes**: Bind dynamic `aria-disabled`, `aria-invalid`, `aria-describedby` based on component props.
- **Keyboard Navigation**: Ensure native focus management remains intact. Provide visible `:focus-visible` states using `--bjj-colors-primary` for outlines.

## Styling Architecture Evaluation

We must decide how to write CSS for these components.

### Approach 1: Vue SFC Scoped Styles (`<style scoped>`)

- **Pros**: Zero CSS collision risk. Vue automatically handles appending unique data attributes to elements.
- **Cons**: Extremely difficult for consuming applications to override specific component internals without relying on the deprecated `::v-deep` or Vue-specific `:deep()` pseudo-selectors. Harder to extract cleanly into a single framework CSS file.

### Approach 2: Unscoped BEM-style CSS (`<style>`) (Recommended)

- **Pros**: Follows industry standards for enterprise UI libraries (like Vuetify, Ant Design, Element Plus). By using a strict namespace (e.g., `.bjj-btn`, `.bjj-input`), we prevent collisions while allowing consumers to easily target and override styles from their own global CSS if necessary. It makes exporting a single `bangjeje-ui.css` trivial.
- **Cons**: Requires strict discipline to adhere to the BEM (Block Element Modifier) naming convention to avoid bleeding styles.

**Recommendation**: Use **Approach 2 (Unscoped BEM CSS)** natively within the `.vue` files. It provides maximum flexibility for consumers while leveraging our predictable `--bjj-*` CSS variables.

## Shared Component Utilities

We will introduce shared composables/utilities within `@bangjeje/ui` to standardize behaviors:

- `useSizeClass(props)`: Returns standardized size modifier classes.
- `useVariantClass(props)`: Returns standardized variant modifier classes.

## Public API / Export Strategy

The `@bangjeje/ui` package will export components via a clean barrel file (`src/index.ts`):

```typescript
export { default as BjjButton } from "./components/button/Button.vue";
export { default as BjjInput } from "./components/input/Input.vue";
// Plus corresponding prop interfaces for advanced consumers
```

We will prepend component names with `Bjj` (e.g., `BjjButton`) to prevent conflicts with native HTML elements in consuming Vue templates, though consumers can rename them on import.

## Build Strategy

Currently, the workspace uses `tsup`. However, `tsup` (esbuild) struggles with complex Vue SFCs and CSS extraction without heavy plugin configuration.
**Recommendation**: Transition `@bangjeje/ui` to use **Vite** in Library Mode (`vite.config.ts` with `vite-plugin-vue`). This is the Vue ecosystem gold standard, ensuring flawless compilation of SFCs, proper `.d.ts` generation (via `vite-plugin-dts`), and clean CSS extraction into a single `style.css` asset.

## Testing Strategy

- **Framework**: `vitest` + `@vue/test-utils`.
- **Focus**: Test prop bindings, event emissions, slot rendering, and ARIA attribute correctness.
- Visual token tests are out of scope (as the theme package handles token resolution).

## Initial Component Scope

We will implement exactly two foundational components to prove this architecture:

1. **`BjjButton`**: Handles clicks, loading states, variants, sizes, and disabled states.
2. **`BjjInput`**: Handles text input, model-binding (`v-model`), disabled states, and error states (invalid ARIA).


## Out of Scope

- Building complex components (Select, Modal, DataGrid).
- Modifying `@bangjeje/core` or changing the core DI plugin architecture.
- Altering the `@bangjeje/tokens` schema.
- Implementing dark mode (deferred to a future theme sprint).

## Risks and Trade-offs

- **Build Tooling Divergence**: Using Vite for `@bangjeje/ui` while using `tsup` for other packages introduces a slight tooling divergence. However, it is standard practice in Vue monorepos (e.g., logic packages use tsup/rollup, Vue packages use Vite).
- **CSS Specificity**: Unscoped BEM relies on consumers not writing overly generic conflicting CSS.

## Acceptance Criteria

- [ ] `@bangjeje/ui` package is scaffolded with Vite library mode.
- [ ] `BjjButton` and `BjjInput` are implemented using Vue SFCs and Unscoped BEM styles.
- [ ] Components strictly use `--bjj-*` CSS Custom Properties for colors, spacing, radius, and typography.
- [ ] Unit tests for both components pass using `@vue/test-utils`.
- [ ] The package successfully builds, extracting a `.css` file and `.d.ts` types.
- [ ] The showcase/playground apps can import and render `BjjButton` without breaking.
